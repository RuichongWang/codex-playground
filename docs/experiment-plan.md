# 实验计划 — 第 1 轮

> 这份文件是给迭代用的：每轮跑完在「结果」和「变更记录」里追加，别覆盖。
> 设计本身在 `pattern-hierarchy-design.md`，这里只管怎么跑、看什么、什么算过关。

状态：**第 1 轮已跑完**（2026-09）。结果见文末。

## 0. 这轮要回答什么

系统的核心命题是：**一群 agent 边干活边猜 pattern，不同来源的具体事件会独立地归到同一个猜测下面。**

这轮不验「有没有用」，只验「**它会不会根本不发生**」。
如果 20 条事件写完，每个 pattern 底下都只挂 1 个 item，汇聚从未发生，那整套设计就是错的，
后面的可信度、prescription、迁移全都无意义。这是最便宜的证伪点，所以先打它。

## 1. 运行方式（已定）

| | 定成 | 理由 |
|---|---|---|
| runtime | `claude -p` 无头调用 | 这台 VM 里凭证是 host 托管的（`CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`），**不需要 API key**，实测可用 |
| 模型 | `--model claude-opus-5` | 阶段 1 看的是判断质量。用弱模型出坏结果会分不清是设计问题还是模型不够 |
| agent 怎么查库 | 给它 `Bash`，让它自己跑 `python -m pk.cli ...` | 「agent 自己跟库交互」是硬要求。这样它自己决定查什么、查几次、什么时候停 —— 不是我用两阶段 prompt 模拟的 |
| 语料 | subagent fan-out 网搜，每个 agent 负责一个行业找真实事件 | 比抓 openFDA/NTSB 好：那些是单一机构的模板化文本，措辞多样性不够，而措辞多样性正是要压测的东西 |

`pk/agent.py`（Anthropic SDK 版）**保留为备选**：它没有 CLI 那 ~40k 系统提示开销，
单次可能便宜一个量级，但需要 API key，且查库得靠写死的两阶段 prompt。
阶段 2 要是规模涨到几百条，再换它。

### 成本基线（实测，2026-09）

空调用（只回复 "ok"）的地板价，Claude Code 系统提示每次全量加载，`--allowed-tools "" --strict-mcp-config` 压不掉：

```
claude -p --model claude-sonnet-5   $0.038 / 次
claude -p --model claude-opus-5     $0.095 / 次
```

按 ~90 次调用估，阶段 1–3 约 **$10–15**（真实 prompt 比空调用大，实际会更高），
加语料 fan-out 整轮约 **$15–25**。

## 2. 阶段

### 阶段 1 — 单条写入的质量（~20 次调用）

一条经历喂进去，看 agent 猜出来的东西长什么样。**这一步是人看，不是指标看。**

观察项：

1. **条件粒度** —— 「两个节奏之间的东西可存储」（可复用）vs「周末骨干只有一半」（就是在描述那一个 item）。一次性条件占比高就是要淹库。
2. **猜的数量** —— 一条 item 猜出 8 个 pattern 就是要爆炸。
3. **该 link 没 link** —— 库里明明有对的，agent 查库时没找到，或找到了没 link。
4. **同情境自报准不准** —— 见 §3，这是这轮新引入的机制，第一次见真章。

出口条件：没有系统性的坏毛病（不是「完美」，是「没有一眼就看出来的结构性问题」）。

### 阶段 2 — 汇聚（~60 次调用，20 条事件）

按顺序喂进库，看汇聚有没有真的发生。**这是这轮的主命题。**

指标：

- `已有 pattern 被复用的比例` —— 写入时 link 到已有 pattern 的次数 / 总 link 次数
- `最大 pattern 的独立事件数` —— 有没有出现真正被多方撑起来的猜测
- `pattern 数 / item 数` —— **爆炸系数**。接近 1 说明每个 item 各猜各的，从不汇聚

出口条件：至少出现 2–3 个独立事件数 ≥ 3 的 pattern，且爆炸系数明显小于 1。

### 阶段 3 — 迁移（~10 次调用）

留 5 条事件不写入，让 agent 只靠库去解。对照三组：

- 裸模型（无库）
- 只有 item、没有 pattern（等价于 case-based reasoning）
- 全库（pattern + condition + prescription）

**这是唯一能说明「这套东西有用」的一步**，前两阶段都只是在保证它没坏。

## 3. 这轮改掉的一件事：不用 embedding，改 agent 自报

原方案用字面相似度（`SIM_THRESH=0.35`，字符 bigram Jaccard）给事件聚簇，
用簇数当「独立事件数」。这个东西在中文短文本上很脆：同一情境换个说法就被算成两个独立事件，
不同情境撞词又会被合并 —— 而它是所有可信度的地基。

**改成：link 的时候让 agent 自己声明**「已经挂在这个 pattern 下的事件里，
有没有跟我这件事本质上是同一个情境？」有 → 标成同情境的又一次确认；没有 → 算新的独立事件。

为什么这样更好：
- 不需要 embedding、不需要阈值
- 跟整个系统的哲学一致 —— 所有判断都是模型做的、靠汇聚验证，不靠写死的函数
- 原计划的「阶段 0：聚簇单元测试」因此**取消**

风险：自报可能不准，也可能被刷（一个 agent 一直声称自己是新情境）。
对冲是后来的 agent 看到会觉得不对，可以打负 link 或提合并。先跑，观察再说。

**⚠️ 待改代码**：`pk/store.py` 里 `_independent()` / `SIM_THRESH` / `_sig()` 还是旧的字面相似度版本，
要换成读 link 上的自报字段。这件事跟 `pk/cli.py` 一起做。

## 4. 预判会先坏的三件事（按概率）

1. **条件粒度** —— 一次性条件淹库。
2. **猜测发散、永远撞不上** —— 每个 item 各猜各的，汇聚从不发生。
   **最致命，因为它不是 bug 是设计问题。** 缓解手段是 prompt 里强制先查库 + 优先复用已有 pattern，
   但那会引入相反的偏差（什么都往已有的上靠），所以必须**同时盯假 link 率**。
3. **同情境自报不准** —— 新引入的机制，没有先例。

## 5. 执行顺序

1. `pk/cli.py` —— 把 store 包成命令行（search / get / neighbors / write / link / prescribe / score），给 agent 当工具
2. 顺手把 §3 的自报字段替掉字面相似度
3. 语料 fan-out —— subagent 按行业搜真实事件，落成结构化语料文件
4. 阶段 1 的 20 条
5. 看结果决定阶段 2 怎么调

## 结果

### 第 1 轮（30 条真实事件，6 批 × 5，opus-5，$41.85）

**主命题成立：汇聚真的发生，而且是跨批的。**

| 指标 | 值 |
|---|---|
| 规模 | 事件 30 / pattern 161 / 条件 68 / link 511 / prescription 72 |
| 最强 pattern | 独立事件 21、来源 21、反驳 1 |
| **跨批复用率** | 事件→pattern 的 337 条 link 里 **192 条（57%）指向别的批次建的 pattern** |
| 层级 | pattern→pattern 边 174 条；阶 2+ 的 pattern 38 / 161 |
| 负 link | 83 条 |
| 同情境自报 | **0 条 —— 这个机制一次都没被触发，因此未经验证** |

57% 这个数字是主命题的核心证据：提议 agent 看的是冻结快照、互相不可见、语料交错，
它们撞上的是**另一批 agent 从另一批事件里抽出来的**东西。

**爆炸系数没解决。** 8.20 → 5.37，但那主要是分母在涨：

| 批 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 每事件新建 pattern | 8.2 | 4.8 | 5.0 | 5.8 | 5.0 | 3.4 |

从 8.2 掉到 ~5 之后就平了，批 4 还反弹。**这是提议阶段的产出粒度问题，triage 修不了**
（全程 6 次 triage 只归并了 11 组）。第 2 轮必须在提议 prompt 上加配额或要求自排序取前 N。

**架构上的三个结论**

1. **triage 不能当抄写员。** 旧设计让它重写整份 60KB 的合并 JSON：550s / \$1.85 / 无人校验它有没有改动别人的原话。
   改成只输出归并映射（~1.2KB）+ 代码机械搬运后：**215s / \$0.83**，而且「不许发明」从 prompt 规矩变成结构上做不到。
   常驻断言（写入的每一句必须在某份提议里一字不差出现）全程 6 批全通过。
2. **提议必须结构性隔离**，不能靠 prompt 叮嘱：只读快照副本 + 产出是计划文件而非写操作。
3. **batch 内并行 + batch 间串行**是对的：批内消掉顺序偏差，批间保住「后来者独立撞上」这个主信号。

**修掉的指标 bug**：`sources` 原来只数直接 link，而高阶 pattern 的直接支持者是 pattern（往往只有两三条边），
于是「21 个事件、21 个提出者」被误报成「2 个来源」——**恰恰在高阶抽象上系统性低估**。
改成按落地事件的提出者算。

**解法侧的硬信号出现了**：72 条 prescription 里 3 条有失败记录，且失败原因精确指向缺失的条件。
例：「人工旁路止血」在一处 worked、另一处 failed，失败注记是
「78000 条/周期 vs 千人级人力」——正好是另外两个 agent 独立提出并被归并的那条闸门
（受影响件数 ÷ 硬期限内人工产能）。**「失败的第一反应不是删 prescription，是补出缺失的条件」在真实数据上跑通了。**

### 语料口径：目前只有 incident，这是个真问题（第 3 轮处理）

前两轮的语料全是「出事并且查清了原因」的事件。这不只是覆盖面窄，有两个更硬的后果：

1. **库偏成一本病理学。** 每个现象 pattern 讲的都是「东西怎么坏的」。但这套系统本该也装
   「正常是怎么运转的」「这一行的标准做法是什么」——行业通识和教科书里的东西同样是 pattern。
2. **更要命：incident 是按结果筛选出来的。** 我们只看到机制导致灾难的那些实例。
   于是「共因工况下裕度归零」攒到 20 条佐证，但我们**对同样的配置没出事的情况一无所知**。
   库分不清「这个机制危险」和「这个机制很常见、偶尔出事」——**这是认识论上的缺陷，不只是覆盖率问题。**

第 3 轮加入通识/教科书/正常运转的案例，但有一条设计约束：

**通识条目必须以 item（证据）身份进库，不能以 pattern（假说）身份直接注入。**
一本教科书本身就是别人建好的 pattern 层级；把它当 pattern 灌进去等于从外部走私一套现成的层级，
破坏「一切都是猜出来再靠汇聚验证」这个前提。教科书的主张只是**某个来源的断言**，
它得跟别的东西一样去挣自己的 link。

顺带一个预期收益：教科书主张正是**负 link 最该发生的地方**——
「通识说 X」撞上「某个 incident 显示 X 在某条件下不成立」，直接产出一条缺失的条件。

**第 2 轮仍然只用 incident**，因为它的设计是「新一批事件打第 1 轮冻结的库」，
混入不同**类型**的来源会污染跨批汇聚这个测量。类型变量留给第 3 轮单独变。

### 第 2 轮的设计（已定）

- **30 条新事件、1 批 30 个**，全部对着第 1 轮**冻结**的库提议。零顺序效应，
  「独立撞上」测得比第 1 轮更纯——他们撞上的是完全另一批人建的东西。
- **triage 单级通读，不分组。** 30 份 ≈ 60–80k token，1M 上下文里很宽松；
  分组会系统性丢掉跨组归并，而且模型是通读聚类，不是两两比较。
- 并发封顶（~10 滚动），纯进程层面的事，语义上仍是一批。
- **提议阶段加配额**，治爆炸系数。
- 新语料换一批行业（金融风控、农业、建筑工程、餐饮连锁、公共卫生、赛事运营）拉大跨度。
- 待验证：**同情境自报**第 1 轮一次都没触发，第 2 轮要专门设计能触发它的语料。
