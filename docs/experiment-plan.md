## 0. 这轮要回答什么

系统的核心命题是：**一群 agent 边干活边猜 pattern，不同来源的具体事件会独立地归到同一个猜测下面。**

这轮不验「有没有用」，只验「**它会不会根本不发生**」。
如果 20 条事件写完，每个 pattern 底下都只挂 1 个 item，汇聚从未发生，那整套设计就是错的，
后面的可信度、prescription、迁移全都无意义。这是最便宜的证伪点，所以先打它。

## 1. 运行方式（已定）

| | 定成 | 理由 |
|---|---|---|
| runtime | `claude -p` 无头调用 | 这台 VM 里凭证是 host 托管的（`CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`），**不需要 API key**，实测可用 |
| 模型 | `--model claude-opus-5` | 阶段 1 看的是判断质量。用弱模型出坏结果会分不清是设计问题还是模型不够 |
| agent 怎么查库 | 给它 `Bash`，让它自己跑 `python -m pk.cli ...` | 「agent 自己跟库交互」是硬要求。这样它自己决定查什么、查几次、什么时候停 —— 不是我用两阶段 prompt 模拟的 |
| 语料 | subagent fan-out 网搜，每个 agent 负责一个行业找真实事件 | 比抓 openFDA/NTSB 好：那些是单一机构的模板化文本，措辞多样性不够，而措辞多样性正是要压测的东西 |

`pk/agent.py`（Anthropic SDK 版）**保留为备选**：它没有 CLI 那 ~40k 系统提示开销，
单次可能便宜一个量级，但需要 API key，且查库得靠写死的两阶段 prompt。
阶段 2 要是规模涨到几百条，再换它。

### 成本基线（实测，2026-09）

空调用（只回复 "ok"）的地板价，Claude Code 系统提示每次全量加载，`--allowed-tools "" --strict-mcp-config` 压不掉：

```
claude -p --model claude-sonnet-5   $0.038 / 次
claude -p --model claude-opus-5     $0.095 / 次
```

按 ~90 次调用估，阶段 1–3 约 **$10–15**（真实 prompt 比空调用大，实际会更高），
加语料 fan-out 整轮约 **$15–25**。

## 2. 阶段

### 阶段 1 — 单条写入的质量（~20 次调用）

一条经历喂进去，看 agent 猜出来的东西长什么样。**这一步是人看，不是指标看。**

观察项：

1. **条件粒度** —— 「两个节奏之间的东西可存储」（可复用）vs「周末骨干只有一半」（就是在描述那一个 item）。一次性条件占比高就是要淹库。
2. **猜的数量** —— 一条 item 猜出 8 个 pattern 就是要爆炸。
3. **该 link 没 link** —— 库里明明有对的，agent 查库时没找到，或找到了没 link。
4. **同情境自报准不准** —— 见 §3，这是这轮新引入的机制，第一次见真章。

出口条件：没有系统性的坏毛病（不是「完美」，是「没有一眼就看出来的结构性问题」）。

### 阶段 2 — 汇聚（~60 次调用，20 条事件）

按顺序喂进库，看汇聚有没有真的发生。**这是这轮的主命题。**

指标：

- `已有 pattern 被复用的比例` —— 写入时 link 到已有 pattern 的次数 / 总 link 次数
- `最大 pattern 的独立事件数` —— 有没有出现真正被多方撑起来的猜测
- `pattern 数 / item 数` —— **爆炸系数**。接近 1 说明每个 item 各猜各的，从不汇聚

出口条件：至少出现 2–3 个独立事件数 ≥ 3 的 pattern，且爆炸系数明显小于 1。

### 阶段 3 — 迁移（~10 次调用）

留 5 条事件不写入，让 agent 只靠库去解。对照三组：

- 裸模型（无库）
- 只有 item、没有 pattern（等价于 case-based reasoning）
- 全库（pattern + condition + prescription）

**这是唯一能说明「这套东西有用」的一步**，前两阶段都只是在保证它没坏。

## 3. 这轮改掉的一件事：不用 embedding，改 agent 自报

原方案用字面相似度（`SIM_THRESH=0.35`，字符 bigram Jaccard）给事件聚簇，
用簇数当「独立事件数」。这个东西在中文短文本上很脆：同一情境换个说法就被算成两个独立事件，
不同情境撞词又会被合并 —— 而它是所有可信度的地基。

**改成：link 的时候让 agent 自己声明**「已经挂在这个 pattern 下的事件里，
有没有跟我这件事本质上是同一个情境？」有 → 标成同情境的又一次确认；没有 → 算新的独立事件。

为什么这样更好：
- 不需要 embedding、不需要阈值
- 跟整个系统的哲学一致 —— 所有判断都是模型做的、靠汇聚验证，不靠写死的函数
- 原计划的「阶段 0：聚簇单元测试」因此**取消**

风险：自报可能不准，也可能被刷（一个 agent 一直声称自己是新情境）。
对冲是后来的 agent 看到会觉得不对，可以打负 link 或提合并。先跑，观察再说。

**⚠️ 待改代码**：`pk/store.py` 里 `_independent()` / `SIM_THRESH` / `_sig()` 还是旧的字面相似度版本，
要换成读 link 上的自报字段。这件事跟 `pk/cli.py` 一起做。

## 4. 预判会先坏的三件事（按概率）

1. **条件粒度** —— 一次性条件淹库。
2. **猜测发散、永远撞不上** —— 每个 item 各猜各的，汇聚从不发生。
   **最致命，因为它不是 bug 是设计问题。** 缓解手段是 prompt 里强制先查库 + 优先复用已有 pattern，
   但那会引入相反的偏差（什么都往已有的上靠），所以必须**同时盯假 link 率**。
3. **同情境自报不准** —— 新引入的机制，没有先例。

## 5. 执行顺序

1. `pk/cli.py` —— 把 store 包成命令行（search / get / neighbors / write / link / prescribe / score），给 agent 当工具
2. 顺手把 §3 的自报字段替掉字面相似度
3. 语料 fan-out —— subagent 按行业搜真实事件，落成结构化语料文件
4. 阶段 1 的 20 条
5. 看结果决定阶段 2 怎么调
