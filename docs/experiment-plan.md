# 实验计划 — 第 1 轮

> 这份文件是给迭代用的：每轮跑完在「结果」和「变更记录」里追加，别覆盖。
> 设计本身在 `pattern-hierarchy-design.md`，这里只管怎么跑、看什么、什么算过关。

状态：**第 1 轮已跑完**（2026-09）。结果见文末。

## 0. 这轮要回答什么

系统的核心命题是：**一群 agent 边干活边猜 pattern，不同来源的具体事件会独立地归到同一个猜测下面。**

这轮不验「有没有用」，只验「**它会不会根本不发生**」。
如果 20 条事件写完，每个 pattern 底下都只挂 1 个 item，汇聚从未发生，那整套设计就是错的，
后面的可信度、prescription、迁移全都无意义。这是最便宜的证伪点，所以先打它。

## 1. 运行方式（已定）

| | 定成 | 理由 |
|---|---|---|
| runtime | `claude -p` 无头调用 | 这台 VM 里凭证是 host 托管的（`CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`），**不需要 API key**，实测可用 |
| 模型 | `--model claude-opus-5` | 阶段 1 看的是判断质量。用弱模型出坏结果会分不清是设计问题还是模型不够 |
| agent 怎么查库 | 给它 `Bash`，让它自己跑 `python -m pk.cli ...` | 「agent 自己跟库交互」是硬要求。这样它自己决定查什么、查几次、什么时候停 —— 不是我用两阶段 prompt 模拟的 |
| 语料 | subagent fan-out 网搜，每个 agent 负责一个行业找真实事件 | 比抓 openFDA/NTSB 好：那些是单一机构的模板化文本，措辞多样性不够，而措辞多样性正是要压测的东西 |

`pk/agent.py`（Anthropic SDK 版）**保留为备选**：它没有 CLI 那 ~40k 系统提示开销，
单次可能便宜一个量级，但需要 API key，且查库得靠写死的两阶段 prompt。
阶段 2 要是规模涨到几百条，再换它。

### 成本基线（实测，2026-09）

空调用（只回复 "ok"）的地板价，Claude Code 系统提示每次全量加载，`--allowed-tools "" --strict-mcp-config` 压不掉：

```
claude -p --model claude-sonnet-5   $0.038 / 次
claude -p --model claude-opus-5     $0.095 / 次
```

按 ~90 次调用估，阶段 1–3 约 **$10–15**（真实 prompt 比空调用大，实际会更高），
加语料 fan-out 整轮约 **$15–25**。

## 2. 阶段

### 阶段 1 — 单条写入的质量（~20 次调用）

一条经历喂进去，看 agent 猜出来的东西长什么样。**这一步是人看，不是指标看。**

观察项：

1. **条件粒度** —— 「两个节奏之间的东西可存储」（可复用）vs「周末骨干只有一半」（就是在描述那一个 item）。一次性条件占比高就是要淹库。
2. **猜的数量** —— 一条 item 猜出 8 个 pattern 就是要爆炸。
3. **该 link 没 link** —— 库里明明有对的，agent 查库时没找到，或找到了没 link。
4. **同情境自报准不准** —— 见 §3，这是这轮新引入的机制，第一次见真章。

出口条件：没有系统性的坏毛病（不是「完美」，是「没有一眼就看出来的结构性问题」）。

### 阶段 2 — 汇聚（~60 次调用，20 条事件）

按顺序喂进库，看汇聚有没有真的发生。**这是这轮的主命题。**

指标：

- `已有 pattern 被复用的比例` —— 写入时 link 到已有 pattern 的次数 / 总 link 次数
- `最大 pattern 的独立事件数` —— 有没有出现真正被多方撑起来的猜测
- `pattern 数 / item 数` —— **爆炸系数**。接近 1 说明每个 item 各猜各的，从不汇聚

出口条件：至少出现 2–3 个独立事件数 ≥ 3 的 pattern，且爆炸系数明显小于 1。

### 阶段 3 — 迁移（~10 次调用）

留 5 条事件不写入，让 agent 只靠库去解。对照三组：

- 裸模型（无库）
- 只有 item、没有 pattern（等价于 case-based reasoning）
- 全库（pattern + condition + prescription）

**这是唯一能说明「这套东西有用」的一步**，前两阶段都只是在保证它没坏。

## 3. 这轮改掉的一件事：不用 embedding，改 agent 自报

原方案用字面相似度（`SIM_THRESH=0.35`，字符 bigram Jaccard）给事件聚簇，
用簇数当「独立事件数」。这个东西在中文短文本上很脆：同一情境换个说法就被算成两个独立事件，
不同情境撞词又会被合并 —— 而它是所有可信度的地基。

**改成：link 的时候让 agent 自己声明**「已经挂在这个 pattern 下的事件里，
有没有跟我这件事本质上是同一个情境？」有 → 标成同情境的又一次确认；没有 → 算新的独立事件。

为什么这样更好：
- 不需要 embedding、不需要阈值
- 跟整个系统的哲学一致 —— 所有判断都是模型做的、靠汇聚验证，不靠写死的函数
- 原计划的「阶段 0：聚簇单元测试」因此**取消**

风险：自报可能不准，也可能被刷（一个 agent 一直声称自己是新情境）。
对冲是后来的 agent 看到会觉得不对，可以打负 link 或提合并。先跑，观察再说。

**⚠️ 待改代码**：`pk/store.py` 里 `_independent()` / `SIM_THRESH` / `_sig()` 还是旧的字面相似度版本，
要换成读 link 上的自报字段。这件事跟 `pk/cli.py` 一起做。

## 4. 预判会先坏的三件事（按概率）

1. **条件粒度** —— 一次性条件淹库。
2. **猜测发散、永远撞不上** —— 每个 item 各猜各的，汇聚从不发生。
   **最致命，因为它不是 bug 是设计问题。** 缓解手段是 prompt 里强制先查库 + 优先复用已有 pattern，
   但那会引入相反的偏差（什么都往已有的上靠），所以必须**同时盯假 link 率**。
3. **同情境自报不准** —— 新引入的机制，没有先例。

## 5. 执行顺序

1. `pk/cli.py` —— 把 store 包成命令行（search / get / neighbors / write / link / prescribe / score），给 agent 当工具
2. 顺手把 §3 的自报字段替掉字面相似度
3. 语料 fan-out —— subagent 按行业搜真实事件，落成结构化语料文件
4. 阶段 1 的 20 条
5. 看结果决定阶段 2 怎么调

## 阶段 3（迁移）的评分方案 —— 预注册，跑之前定死

核心原则：**能不用 judge 就不用**。judge 打分是这类实验最大的噪音源，
所以评分做成三层，越硬的层权重越高。

### 第 1 层 客观、无 judge：预测题

给现场情况，然后问：「有人提议做 X（就是当时实际采取的干预）。会成功还是失败？
给理由、关键条件、成功概率 0–100。」ground truth 里有实际结果，直接判对错。

用 **Brier score**（`(预测概率 − 实际结果)²`）而非准确率 —— 严格适当评分规则，
**自信答错罚得比含糊答错重**，n=30 时比准确率灵敏，且能测「库有没有改善校准」。
案例配比控成 worked/failed 各半，防止靠猜一边刷分。

### 第 2 层 半客观：条件命名的元素级 F1（**主指标**）

库唯一声称的独特价值，所以是主指标。把「哪个更好」拆成「**含不含某个具体元素——是/否**」：

1. **预注册 checklist**：在看到任何 arm 的答案之前，只根据源材料写出决定成败的条件清单（E1/E2/…）
2. **逐元素判定**：judge 每次只回答一个二元问题「有没有说到 E2」，不做整体质量评价
3. **算 F1，不是召回**：
   - Recall = 真条件里被说到的比例
   - Precision = 答案提到的条件里确实在清单上的比例
   - **必须用 F1** —— 只看召回的话，把二十条可能条件全撒出来的答案会赢，
     那正是「硬套模板」失败模式（skill 方案误用率 10.0% vs 原始执行 0.8%）

### 第 3 层 配对盲比：只用在拆不开的地方

「机制诊断哪份更接近真实根因」这类整体判断才用。同一案例两份答案随机成 X/Y，
judge 不知道哪个是哪个、也不给它看库。符号检验。**权重最低，只作参考。**

### 判定规则

| 结论 | 判据 |
|---|---|
| **库有用** | 条件 F1：**C − D ≥ 15 个百分点**，配对符号检验 p<0.05 |
| **库改善判断质量** | Brier：C 显著低于 D |
| **抽象层有用** | C − B 同样达标（否则检索原始案例就够，pattern 层白建） |
| **安慰剂有效** | D ≈ A。若 D > A，说明「有材料读就有帮助」，C 对 A 的优势虚高，须单独报 |
| **实验无效** | 污染分层后「模型认不出」的案例 < 10 条 → 结论是「没测出来」，不是「没用」 |

**最关键的一格：认不出的那一层里，C 的条件 F1 减 D 的条件 F1。那一个数就是整个项目的答案。**

### held-out 的选取标准

选择标准直接决定实验能测出什么：挑跟库里像的，C 赢得毫无意义；挑毫无关系的，null 是构造出来的。
且**不能**按「库里有没有对应机制」挑 —— 那是按结果选样本。所以用跟库无关的轴分层，覆盖率事后当结果报：

1. **按行业排除法选，选的 agent 不许看库** —— 只从前三轮没覆盖过的行业取
   （采矿、渔业、军事后勤、影视制作、司法、监狱、档案、太空、极地、拍卖、职业体育…）
2. **ground truth 必须齐三样**：有据可查的根因 + 实际干预 + 干预结果
3. **至少 1/3 是「干预失败」的案例** —— 第 1 层硬指标的来源
4. **优先 2026 年 6 月之后的事件** —— 知识截止是 2026 年 5 月，这个窗口污染为零，是构造保证的
5. **放一组阴性对照**：机制在库里确实不存在的案例。若 C 在这些上也「有帮助」，
   说明帮助是泛化的、与具体 pattern 无关 —— 这是对 D 的组内交叉检验

### 安慰剂 D 怎么造

**不能是乱码** —— 模型一眼看穿就直接忽略，D 退化成 A，安慰剂失效。

**D = 张冠李戴的真库内容**：结构、质量、篇幅完全一样，但喂给案例 i 的是为案例 j 检索的 pattern。
内容全是真的、连贯的、高质量的，**只是不对症**。不做真正的匹配工作就分辨不出来。标准的活性安慰剂。

## 阶段 3 结果 —— **null，而且实验本身也没有检出能力**

30 个 held-out 案例 × 4 个 arm，$46.75。**结论：没有检出库带来的任何收益；
但同样重要的是，这个实验设计**本来也检不出**，因为题目太简单。**

### 污染分层（这一关过了）

模型认得出且根因也对得上：15 / 认不出或根因对不上：15。
干净样本 15 条 ≥ 预注册门槛 10 条，**所以「实验无效」这条不适用，污染不是限制因素**。

### 结果（只在四臂都给出可解析输出的交集上算）

| 干净样本 n=11 | A 裸模型 | B 只有case | C 全库 | D 安慰剂 |
|---|---|---|---|---|
| 条件 F1 | 0.822 | 0.819 | **0.799** | 0.830 |
| precision | 0.867 | 0.815 | 0.786 | 0.836 |
| recall | 0.800 | 0.836 | 0.818 | 0.855 |
| Brier | 0.015 | 0.017 | 0.013 | 0.013 |
| 预测准确率 | 1.000 | 1.000 | 1.000 | 1.000 |
| （全押 failed 基线） | | | | 0.909 |

C 在每个分层的条件 F1 上都是**名义最低**，但一次都不显著（p=0.508 ~ 1.000）。
配对盲比 C vs D 13:9、C vs B 15:11，同样不显著。

### 真正的问题：天花板效应，不是库没用

**裸模型在干净样本上预测准确率已经是 1.000，条件 F1 已经 0.82。没有余量可涨。**

三个原因，都是我的设计问题：

1. **题面虽然不泄露答案，但仍含有足够的判据。** 我自己在给用户举例时就演示过：
   El Teniente 那题的两个致命线索（「事先看不到可用的前兆」「比历史管理过的深度更深」）
   就写在题面里。强模型只要读得仔细就够了，不需要库。
2. **conditions 清单是同一族模型从同一份源材料写出来的**，所以另一个模型读题面就能收敛到 ~82%。
   这个 checklist 测的是「读题仔细程度」，不是「有没有可迁移的抽象」。
3. **全押 failed 的基线在干净子集上就有 0.909**，预测题几乎没有区分度。

### 一个真实的负面发现

**C 和 D 各有 4/30 个案例没能吐出可解析的 JSON，A 和 B 是 0/30。**
长上下文（库内容）明显降低了格式遵从率。这是真实代价，跟内容对不对症无关 ——
D 也一样坏，说明是篇幅本身的问题。

### 差点被当成结论的一个统计错误

首轮报表在**各臂各自的有效子集**上取 Brier 均值：C 因为 3 个案例没吐概率（恰好都是难题），
均值从 0.064 掉到 0.014，看起来「C 让判断质量提升 5 倍」。
在四臂共同子集上重算，四个臂是 0.013~0.017，**毫无差别**。
已修（`pk/report3.py` 现在强制用交集）。**这个坑值得记住：不等长的臂之间不能直接比均值。**

### 下一轮要改什么

这一轮真正学到的是**怎么把题出难**，而不是库有没有用：

1. **不给干预，让 agent 自己提。** 现在是「判断这个干预行不行」（二选一，天花板极低），
   应该是「你会怎么做」，再拿它跟实际奏效的做法比。余量大得多。
2. **checklist 必须包含从题面推不出来的条件。** 现在的清单是题面的仔细读解；
   要测迁移，条件得需要**案例之外的知识**才写得出来。
3. **题面再削一层**，只留症状，把背景约束（那些恰好是判据的句子）也拿掉。
4. **平衡 outcome 配比**，让「全押一边」的基线降到 0.5 附近。

held-out 集合本身没浪费 —— 30 个案例的 ground truth、条件清单、污染标注都还在，
换一种问法就能复用。

## 读取侧改成 agentic：库是环境，不是塞进去的材料

静态 top-8 注入被换成「Bash + CLI + skill」，四个 arm 工具完全一样，
差别只在指向哪个库、检索准不准。安慰剂随之改成**盲检索**（同一个全库、同样的工作量，
但 search 返回与查询无关的真节点）—— 喂错内容在 agent 能自己查之后就不可比了，它会重查一遍。

`.claude/skills/pattern-library/SKILL.md` 教的是**怎么走库**，不是命令表。
第一次带轨迹的运行（14 次工具调用）显示六条教法全部落到行为上：
读 skill → 13 种**机制层面**的查法（无一个领域词）→ 用 for 循环把 7 个查询打包成 1 轮
→ `catalog` 导出全库自己筛 → 逐个 `neighbors` 展开 → 列全部 177 条条件并查 prescription
→ **明确写下「库里没有传媒或产业政策的事件」然后只在机制层面找，没有硬套**。

结果正确（failed / 概率 20），且推理里直接引用了 `I36`（日本注射器死腔与瓶剂量不匹配）
和 `C106` —— 跨域迁移在真实发生。16 轮 / 225 秒 / $1.33。

## 阶段 4 结果 —— 第三次撞天花板，但过程指标很硬（$119.75）

题改成「不给干预、自己提方案」，主指标换成陷阱规避（17 个案例的真实干预是失败的，
那是真实世界验证过的坑）。臂精简为 A（无库）/ C（有库，agentic：Bash + skill + CLI）。

### 结果指标：又一次打平

| 陷阱题 n=17 | A 无库 | C 有库 |
|---|---|---|
| 走进陷阱 | 0.0% | 0.0% |
| 点出致命缺陷 | 94.1% | 100.0% |
| **规避率（主指标）** | **100%** | **100%** |
| 条件 F1（n=30） | 0.675 | 0.659 |
| 宽松版配对盲判 | C 胜 3 / A 胜 1 / 平 26，p=0.625 | |

**两个臂都真的避开了全部 17 个陷阱**，核过原始判定，不是判官失灵 ——
裸模型被问「你会怎么做」时根本不会提那个天真动作。**陷阱抓不到人。**

两套判分（严格的逐元素 F1、宽松的整体判分）方向一致：都是打平。
按预注册规则，这意味着结论稳 —— 稳在「没有差别」上。

### 过程指标：库被真实、深度、跨域地使用

| | |
|---|---|
| 最终推理里明确引用库节点 | **30/30** |
| 平均碰过的节点 | 157 个（其中 pattern ~110） |
| 阶 2+ 高阶抽象占比 | **21%** |
| 每个案例覆盖的语料域 | **18/18** |

held-out 的六个域（采矿、航天、司法、影视档案、渔业海事、国防）**在库里一条证据都没有**，
所以它引用的每一条都是跨域的。C 自己也清楚这一点，某次运行里主动写道：
「这个库 90 个事件全在电网、供应链、IT 事故、工程项目、公共卫生、农业政策里，
没有一条影视或区域产业政策的事件。我拿到的是**结构同构的假说 + 条件清单，不是本领域证据**。」

### 诚实的结论

- **「库有没有被用上」= 是，非常确定。**
- **「库有没有让结果变好」= 测不出来。** 四个结果指标（条件 F1、Brier、预测准确率、陷阱规避）
  全部在天花板上打平。

**这不是「库没用」，也不是「库有用」，是这个测法在 opus-5 上没有分辨率。**
改了三次题（加难度、拿掉干预泄露、换主指标），三次都撞天花板 ——
问题已经不在题，在被试太强。

### 这一轮修掉的两个 harness bug

1. **无库臂被要求写文件，但它没有任何工具**（`--allowed-tools ""` 是它的定义），
   30 次全部空手而归。改成按臂分流：无库臂直接输出 JSON。
2. **限流失败长得像成功**：`subtype: "success"`、`num_turns: 1`、`cost: 0`，
   只有 `is_error` 和 result 文本能区分。它被写成「已完成但没产出」的记录固化下来，
   续跑看到有记录就跳过，永远不再重试 —— 于是「已完成 60 条」掩盖了「59 条是废的」。
   现在 `is_error` 为真直接抛异常，不落盘。

## ForecastBench 试水 —— 出局，而且是个有价值的负面发现

拉了 ForecastBench 2026-06-07 期（359 道已 resolve，全部在知识截止 2026-05 之后），
按来源分层抽 6 题跑 A/C 两臂。

| | Brier（越低越好） | 成本 |
|---|---|---|
| A 裸模型 | **0.2540** | \$0.85 |
| C 有库 | **0.3519**（差 39%） | \$4.12 |
| 市场价基线 | **0.0426** | — |

**库让它变差了。** 最刺眼的一条：法国某气象站日均气温会不会超阈值 ——
A 预测 68，C 花 11 轮 \$0.65 翻了一个装满工业事故的库之后预测 96，实际 0。
**这不是无用，是干扰**：它在无关材料里找到了「支持」，然后加强了错误判断。

而市场价 0.0426 甩开两臂一个量级，说明这些题本来就有便宜得多的好答案。

分层抽的 6 题（罗马尼亚爆炸事件数、法国气温、美债收益率、中国 GDP、世界杯出线、
伊朗美国是否交手）**没有一道跟库的内容有关**。ForecastBench 的题面分布与本项目正交。

**结论**：不作为主实验，也不必再做「悲观偏差体检」—— 已经看到更直接的东西：
**在无关领域，库是有害的。** 这一条应当进入系统设计：
skill 里「库里没有就说没有」这条规矩不够，需要更强的止损机制。

## 下一个 benchmark 的方向：配对干预题（提案）

**同一个做法，在 A 处成了、在 B 处砸了。给 agent 看 B 处的情况和这个做法，
问：会成还是会砸，哪个条件决定的。**

例：「用人工旁路顶替失灵的系统先撑住业务」——
Nike i2 崩盘时成了；昆士兰工资系统砸了（7.8 万员工 vs 千人级人力，人工吞吐差两个数量级）。

**为什么它能解决撞了三次的天花板**：现在的题全是「出事了」，
模型有极强先验 —— 看起来像事故的就判失败。这就是陷阱题 100% 满分的真相：
它没在推理，在用先验。配对设计里同一个做法正负各半，这条捷径直接失效。

附带三个好处：① 它就是库的原生形状（现象 + 条件 → 解法，问的正是条件满不满足）；
② 可以全用保留域；③ 这个 benchmark 不存在 —— 理论侧（transportability、boundary
conditions、moderator、external validity）很成熟，但没人做成 LLM benchmark。

## 变更记录（为了不重走老路）

| 轮次 | 放弃了什么 | 为什么 |
|---|---|---|
| v0.1 → v0.2 | 「层级已存在、怎么检索」的整个命题（`ph/` 那套） | 方向错了。核心是**写入**，层级是被 link 出来的，不是给定的 |
| v0.2 | MDL 压缩率筛抽象 | 那是单 agent 离线靠信息论。这个系统是多 agent 在线靠汇聚 |
| v0.2 | 「训练域冻结 / 测试域评估」的迁移实验 | 系统里没有训练/测试之分，迁移就是日常查库，硬做成一次性实验是扭曲 |
| v0.3 | `domain` 字段 | 域太大（一条解法在「电力」成立 ≠ 电力任何场景都成立），且「上升到域」本身就是一次抽象，不该预先给定 |
| v0.3 | link 总数计分 | 同一情境反复写就能刷。价值已体现在独立事件数和来源数里 |
| v0.4 | 字面相似度聚簇 + 阶段 0 单元测试 | 改成 agent 在 link 时自报同情境。不用 embedding，跟系统哲学一致 |
| v0.5 | **ForecastBench 当主 benchmark** | 领域不对口。预测题考的是**概率校准**，不是跨域迁移；跑赢也不证明本项目的命题，跑输（实测 Brier 差 39%）只说明库在无关领域是干扰 |
| v0.5 | **双判分（严格逐元素 F1 + 宽松整体判分两套 rubric）** | 两套方向相反时给不出单一结论，只能说「没测稳」；多一套 rubric 就是多一个研究者自由度，**增加自由度反而降低可信度**。第四阶段改成单 judge + 冻结 rubric + 翻转率检查 |
| v0.5 | **继续改题目难度** | 三次改题**都是在看到天花板之后**做的，属于事后调设计：题被调到「能显出差别」为止，差别就不再是测出来的，是选出来的。今后题面冻结，只动库规模和模型两个轴（见 CLAUDE.md 第四条硬规矩） |

## 结果

### 第 1 轮（30 条真实事件，6 批 × 5，opus-5，$41.85）

**主命题成立：汇聚真的发生，而且是跨批的。**

| 指标 | 值 |
|---|---|
| 规模 | 事件 30 / pattern 161 / 条件 68 / link 511 / prescription 72 |
| 最强 pattern | 独立事件 21、来源 21、反驳 1 |
| **跨批复用率** | 事件→pattern 的 337 条 link 里 **192 条（57%）指向别的批次建的 pattern** |
| 层级 | pattern→pattern 边 174 条；阶 2+ 的 pattern 38 / 161 |
| 负 link | 83 条 |
| 同情境自报 | **0 条 —— 这个机制一次都没被触发，因此未经验证** |

57% 这个数字是主命题的核心证据：提议 agent 看的是冻结快照、互相不可见、语料交错，
它们撞上的是**另一批 agent 从另一批事件里抽出来的**东西。

**爆炸系数没解决。** 8.20 → 5.37，但那主要是分母在涨：

| 批 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 每事件新建 pattern | 8.2 | 4.8 | 5.0 | 5.8 | 5.0 | 3.4 |

从 8.2 掉到 ~5 之后就平了，批 4 还反弹。**这是提议阶段的产出粒度问题，triage 修不了**
（全程 6 次 triage 只归并了 11 组）。第 2 轮必须在提议 prompt 上加配额或要求自排序取前 N。

**架构上的三个结论**

1. **triage 不能当抄写员。** 旧设计让它重写整份 60KB 的合并 JSON：550s / \$1.85 / 无人校验它有没有改动别人的原话。
   改成只输出归并映射（~1.2KB）+ 代码机械搬运后：**215s / \$0.83**，而且「不许发明」从 prompt 规矩变成结构上做不到。
   常驻断言（写入的每一句必须在某份提议里一字不差出现）全程 6 批全通过。
2. **提议必须结构性隔离**，不能靠 prompt 叮嘱：只读快照副本 + 产出是计划文件而非写操作。
3. **batch 内并行 + batch 间串行**是对的：批内消掉顺序偏差，批间保住「后来者独立撞上」这个主信号。

**修掉的指标 bug**：`sources` 原来只数直接 link，而高阶 pattern 的直接支持者是 pattern（往往只有两三条边），
于是「21 个事件、21 个提出者」被误报成「2 个来源」——**恰恰在高阶抽象上系统性低估**。
改成按落地事件的提出者算。

**解法侧的硬信号出现了**：72 条 prescription 里 3 条有失败记录，且失败原因精确指向缺失的条件。
例：「人工旁路止血」在一处 worked、另一处 failed，失败注记是
「78000 条/周期 vs 千人级人力」——正好是另外两个 agent 独立提出并被归并的那条闸门
（受影响件数 ÷ 硬期限内人工产能）。**「失败的第一反应不是删 prescription，是补出缺失的条件」在真实数据上跑通了。**

### 语料口径：目前只有 incident，这是个真问题（第 3 轮处理）

前两轮的语料全是「出事并且查清了原因」的事件。这不只是覆盖面窄，有两个更硬的后果：

1. **库偏成一本病理学。** 每个现象 pattern 讲的都是「东西怎么坏的」。但这套系统本该也装
   「正常是怎么运转的」「这一行的标准做法是什么」——行业通识和教科书里的东西同样是 pattern。
2. **更要命：incident 是按结果筛选出来的。** 我们只看到机制导致灾难的那些实例。
   于是「共因工况下裕度归零」攒到 20 条佐证，但我们**对同样的配置没出事的情况一无所知**。
   库分不清「这个机制危险」和「这个机制很常见、偶尔出事」——**这是认识论上的缺陷，不只是覆盖率问题。**

第 3 轮加入通识/教科书/正常运转的案例，但有一条设计约束：

**通识条目必须以 item（证据）身份进库，不能以 pattern（假说）身份直接注入。**
一本教科书本身就是别人建好的 pattern 层级；把它当 pattern 灌进去等于从外部走私一套现成的层级，
破坏「一切都是猜出来再靠汇聚验证」这个前提。教科书的主张只是**某个来源的断言**，
它得跟别的东西一样去挣自己的 link。

顺带一个预期收益：教科书主张正是**负 link 最该发生的地方**——
「通识说 X」撞上「某个 incident 显示 X 在某条件下不成立」，直接产出一条缺失的条件。

**第 2 轮仍然只用 incident**，因为它的设计是「新一批事件打第 1 轮冻结的库」，
混入不同**类型**的来源会污染跨批汇聚这个测量。类型变量留给第 3 轮单独变。

### 第 2 轮结果（30 条一批打第 1 轮冻结的库，$2.99 triage + 提议约 $25）

- **30 条新事件、1 批 30 个**，全部对着第 1 轮**冻结**的库提议。零顺序效应，
  「独立撞上」测得比第 1 轮更纯——他们撞上的是完全另一批人建的东西。
- **triage 单级通读，不分组。** 30 份 ≈ 60–80k token，1M 上下文里很宽松；
  分组会系统性丢掉跨组归并，而且模型是通读聚类，不是两两比较。
- 并发封顶（~10 滚动），纯进程层面的事，语义上仍是一批。
- **提议阶段加配额**，治爆炸系数。
- 新语料换一批行业（金融风控、农业、建筑工程、餐饮连锁、公共卫生、赛事运营）拉大跨度。
- 待验证：**同情境自报**第 1 轮一次都没触发，第 2 轮要专门设计能触发它的语料。

**结果：**

| | 第 1 轮 | 第 2 轮 |
|---|---|---|
| 每事件新建 pattern | 5.4 | **2.43**（加了「最多 3 个」的配额） |
| 复用率 | 57%（跨批） | **77%（跨轮，打的是完全另一批人建的库）** |
| 同情境自报 | 0 次触发 | **1 次，判对；0 次误判** |

**77% 是这套系统最强的一个数。** 30 个提议 agent 互相不可见、看的是冻结快照、
撞上的是上一轮完全另一批 agent 从完全不同的行业事件里抽出来的 pattern。

**同情境机制验证通过。** 专门设计的 5 条配对语料：
- 配对 A（Rogers 2022 断网的监管视角 vs 企业自述视角）→ **判定同情境，理由写对了**：
  「同一起事故…B1A30 明确写了 2022-07-08，B1A22 描述的是同一条时间线的另一半，只是没写日期」
- 配对 B（CrowdStrike 2024 vs Cloudflare 2025，不同公司不同年份、机制雷同）→ **正确地没有标记同情境**
  （它们是两个独立事件，该各算一份证据），但**共同 link 到 4 个相同的 pattern** —— 这正是理想行为
- 干扰项（爱立信证书过期，表层词汇同时贴近两组）→ **没有误判**

**配额有效但不彻底**：每事件 5.4 → 2.43，库仍在以每事件 2.4 个的速度增长。

**踩到的坑**：30 份提议内联进 `claude -p` 的 argv 共 181KB，超 Linux 单参数 128KB 上限（E2BIG）。
改成 prompt 只给文件路径、triage 自己 cat —— 这也更贴合「通读」的本意。
triage 通读 30 份：651s / \$2.99 / 15 轮，归并 3 组 + 映射到已有 3 条。

### 第 3 轮结果（30 条通识/教科书/正面案例打第 2 轮冻结的库，累计 $51.59）

语料构成：教科书原理 20 + 有边界条件的最佳实践 5 + 「本来会出事但没出事」5。

| | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 语料类型 | 事故 | 事故 | **通识/理论/正面案例** |
| 每条新建 pattern | 5.4 | 2.43 | 2.53 |
| 复用率 | 57%（跨批） | 77%（跨轮） | **71%（跨类型）** |
| **负 link / 每条材料** | ~0.9 | ~0.9 | **2.60** |

**跨类型汇聚成立：71%。** 利特尔法则、Kingman 公式、Rasmussen 迁移到边界、公地悲剧
这些教科书原理，落到了前两轮从医院上线事故、电网调度、供应链断供里猜出来的 pattern 下面。
教科书以 item 身份进库、自己去挣 link 这条约束没有削弱它——它照样接得上。

**负 link 是这轮最大的收获：78 条，接近前两轮总和（163）的一半，密度是前两轮的近 3 倍。**
而且形态正是设计时想要的「通识说 X，但库里那条有个没写出来的前提」：

> Bainbridge 自动化讽刺 ⊣ C58（从最后可挽回时刻到全损的窗口，短于人观察—判断—授权—执行这条回路）
> 理由：「这是我手上这条通识没写出来的适用边界，而且它作废的正是这条通识的**结论部分**。
> C58 成立时，无论操作员训练得多好、手感多新、界面多好，对这……」

**意外收获：库反过来限定了教科书。** Goodhart 那条产出的一条负 link，
不是「通识修正库」，是**库修正了通识的过宽转述**：

> Goodhart ⊣ P61（把「真实条件下的预演天数」写成放行硬闸门）
> 理由：「反例（针对流行转述的过宽读法）：P61 明确把预演天数当成日程压力下的考核目标，
> **却没有出现 Goodhart 式失效，且被 8 个独立事件支持。原因是这个量没有旁路**——
> 除了真的把预演跑够……」

这是双向的：教科书给库补边界，库给教科书补反例。**这是原设计里没预料到、但正是它该有的行为。**

90 条材料 / 310 pattern / 177 条件 / 1396 link / 189 prescription，累计约 \$52。
最强 pattern 攒到 65 个独立事件。爆炸系数 8.20 → 3.90 → 3.44。

# 第四阶段：规模斜率实验（预注册）

**日期：2026-09-05。本节在看到任何第四阶段结果之前写下。**
跑完之后这里一个字都不许改 —— 要改就在文末「变更记录」里新起一条，
写清楚改了什么、为什么、以及**是在看到什么之后**改的。

## 4.0 为什么换问题（而不是再改一次题）

前三个阶段问的都是「有库 vs 没库」。四个结果指标、三次改题，**全部撞天花板**。
Anthropic 自己对 skill 的退役判据是：**base model 不带 skill 也能过你的 eval，
说明这个技术已经被模型内化了，该退役这个 skill。**
按这个框架，前三阶段的 null **本身就是一个结果**：opus-5 的权重里已经装了这 90 条事件
能提供的东西。失效的是命题形式，不是库。

所以换两个仍然可证伪、且**不吃天花板**的轴：

1. **规模轴**：同一批题，库 30 / 60 / 90，看**斜率**。斜率是库自己跟自己比出来的 ——
   题目再简单，只要三个规模点面对的是同一批题，天花板对三个点是同一个天花板，
   它压低的是绝对值，不会凭空制造或抹掉斜率。
2. **模型轴**：haiku / sonnet / opus × 有库/无库。命题升级为
   **「库能不能替代模型规模」**。

按第四条硬规矩，**题面和判分方案从此冻结**，能动的只有这两个轴。

## 4.1 主指标 = 斜率（预注册）

- **题目**：`heldout/*.json` 的同一批 30 道，**与阶段 4 完全相同，一个字不改**。
  提问方式沿用阶段 4 的「不给干预、自己提方案」（`pk/eval4.py` 的 `PROMPT`）。
- **库快照**（三个规模点，均为已冻结的历史快照，不重新生成）：

  | 规模点 | 文件 | 事件数 |
  |---|---|---|
  | 30 | `runs/r2/library_round1_frozen.json` | 30 |
  | 60 | `runs/r3/library_round2_frozen.json` | 60 |
  | 90 | `runs/r3/library.json` | 90 |

  三个快照跑之前统一用 `pk/tag_domains.py` 打好域标签，并各跑一次
  `Store.check_integrity()`；每个快照在喂给 agent 之前先过一道
  `--mask`（六个保留域），作为「库确实没见过 held-out 域」的机器可验证断言。

  **⚠️ 这条断言的实际强度（跑之前就写下来）**：库里的域名来自 `corpus*/` 的文件名
  （energy / manufacturing / econ_theory …），保留域的名字来自 `heldout/` 的文件名
  （mining / space / justice / culture / marine / defense），**两边的取值集合零重叠**，
  所以这道 mask 在当前快照上删掉的节点数是 **0**。
  它能挡住的只有一件事：**有人往 `corpus*/` 里加一个叫 `mining.json` 的文件**——
  一旦发生，断言会因为「mask 删掉了东西」而当场失败。
  它**挡不住**的是：一条真正的采矿事故被归到 `manufacturing` 名下写进库。
  因此 **mask 是一道防回归的护栏，不是「库没被污染」的证据**，报结果时不许当证据引用。
  真正承担这件事的是事前纪律（三轮语料的行业清单 + `heldout/HELD_OUT_DOMAINS.md`）。
- **斜率怎么算**（现在写死，实现留到最后）：
  设 `x = log2(库规模 / 30)`，即三个点的横坐标为 `0 / 1 / 1.585`。
  对每个模型 m，把 30 道题在三个规模点上的**得分**对 `x` 做 OLS，
  取一次项系数为该模型的斜率 `β_m`，单位是「库规模翻一倍带来的分数变化」。
  **为什么用 log**：假说本身说的是「价值随规模增长但边际递减」（30 个 item 一次能读完，
  几万个点时那条路根本不存在），线性刻度会把这个形状测成「斜率在衰减」。
  线性刻度的斜率**也要报**，但**现在就定死 log2 是主口径**，免得事后挑一个好看的。
- **CI**（现在写死）：**bootstrap，按 held-out 题 resample（30 题有放回抽 30 题），
  B = 2000，报 95% 百分位 CI。** 同一次 resample 里，一道题在三个规模点上的得分
  必须整组一起进出 —— 三个点共用同一批题，配对结构不能被打散。
  **CI 跨 0 就直说「没测出斜率」**，不许用点估计的符号或「趋势向上」代替。

### 4.1a 这个轴上已知的混杂 —— 跑之前就写下来，免得事后当成发现

**三个规模点不是纯粹的规模轴。** 三个快照的语料构成是：

| 规模点 | corpus（事故） | corpus2（事故） | corpus3（理论/通识/正面案例） |
|---|---|---|---|
| 30 | 30 | 0 | 0 |
| 60 | 30 | 30 | 0 |
| 90 | 30 | 30 | **30** |

所以 30→60 同时变了「事件数」和「行业广度」，60→90 还额外变了**语料类型**
（第 3 轮加进来的教科书原理与「本来会出事但没出事」的案例只存在于 90 里）。
**一个正斜率完全可能来自「理论条目有用」，而不是「库更大有用」。**
这是这个设计当下最大的软肋，写在这里是为了让它不能事后被当成发现。

**能做的对照（不改主设计，作为补充臂）**：用 `Store.mask` 从 90 的库里
每个 corpus 各屏蔽 2 个域，得到一个 **60_mixed** 快照 —— 事件数 60、
三种类型各 20，跟历史 60 的事件数相同而类型比例不同。
若「历史 60」与「60_mixed」的得分差别显著，斜率里就有相当一部分是类型效应，不是规模效应。
注意这两个 60 不是同一种东西：历史 60 的 pattern 层是**在只有 60 条时写出来的**，
60_mixed 的 pattern 层是**在见过 90 条之后写出来、再删掉一部分证据的**，
措辞里仍带着被删那些案例的影子（要堵这一层就得加 `--strict`，但那一刀砍得很深）。

## 4.2 冻结的判分 rubric —— 单 judge（预注册）

**取消双判分**（见变更记录）。改成**一个 judge、一套 rubric、绝对打分**（不是配对比较）——
配对比较给不出跨三个规模点的连续量，做不了斜率。

- judge 模型**固定为 `claude-opus-5`**，不随被试模型变。被试换成 haiku 时判官不能跟着换，
  否则模型轴和判分噪声混在一起。
- judge 看得到 ground truth（`root_cause` / `intervention` / `outcome` / `conditions`），
  看不到这份答案来自哪个臂、哪个模型、哪个规模点。

**rubric（0–6 分，三维各 0/1/2 累加，主指标 = 总分 / 6）：**

| 维 | 2 分 | 1 分 | 0 分 |
|---|---|---|---|
| **M1 机制诊断** | 指出了真实根因所在的那个变量/层位 | 方向对但停在表层症状 | 指错，或指向一个与真实根因无关的东西 |
| **M2 干预选点** | 提出的干预动的正是真正决定成败的那个变量 | 部分相关，但主动作动错了地方 | 无关；或走进了已知会失败的做法**且**没说出它为什么会失败 |
| **M3 条件清单** | 至少一条条件是**从题面推不出来、需要案例之外的知识**的，且正确 | 条件都正确但全是题面的复述 | 条件错、或空、或撒了一堆没用的（列一条没用的比漏一条更糟） |

M3 是这套 rubric 里唯一直接对准本项目命题的一维：库若有用，用处应当首先出现在
「说出了题面里没有的那一条」上。前三阶段的条件 F1 恰恰测不到这个 ——
它的清单是同一族模型从同一份源材料写出来的（见阶段 3 结果第 2 点）。

## 4.3 judge 翻转率检查（预注册）

同一批答案，用**同一套 rubric** 判两遍（第二遍换随机种子、并把三维的呈现顺序和
答案的呈现顺序打乱），报**不一致率**（两遍总分不同的答案占比，以及平均绝对差）。

**不一致率 > 10% ⇒ judge 自身噪声压过效应**，此时任何斜率结论都不成立，
报告里必须写「判分噪声挡住了测量」，而不是「没有效果」。
这一条是「没效果」和「没测出来」的分界线，先于所有结果解读。

## 4.4 shadowing 分解（预注册：斜率为负时的必答题）

库变大**可能反而变差**。已有的直接证据：arXiv 2605.24050 —— skill 库从 52 条扩到 202 条，
通过率掉 21%，其中 **68% 的下降来自选错 skill**，不是来自 skill 本身写错。
本项目自己也见过同型现象：ForecastBench 那一轮里，库让 Brier 差了 39%，
机制是「在无关材料里找到了『支持』，然后加强了错误判断」。

所以**每个规模点都必须拆出三个数**（`pk/transfer.py` 出，离线从轨迹算，不额外花钱）：

- **(a) 命中率** = 最终答案里被引用的库节点数 ÷ 检索过程中触达的库节点数。
  库变大而命中率掉，说明检索被稀释了。
- **(b) 误导率** = 被引用的节点里，**引用了反而扣分**的那些占比。
  判定口径（写死）：该题在该 cell 的 rubric 总分 **低于**同题同模型的无库臂总分时，
  这份答案里引用的节点计为「误导嫌疑」。这是一个**代理量**，不是因果判定，
  报告时必须按代理量报；如果另外做了逐节点的 judge 判定（`misled.jsonl`），以判定结果为准。
- **(c) 平均触达节点数** —— 工作量本身。库变大它必然涨，涨得太快说明 agent 在库里迷路。

**斜率为负时，必须用这三个数说明是 shadowing 还是别的原因**，不许只报一个负数了事。
判据：命中率随规模下降 + 误导率随规模上升 ⇒ shadowing；
三个数都平而斜率仍为负 ⇒ 不是 shadowing，是别的东西，如实说不知道是什么。

## 4.5 安慰剂降级：只在最大规模点跑一次

`PK_BLIND_SEARCH=1` 的盲检索安慰剂臂**只在库 90 这一个规模点跑一次**，不是每个规模点都跑。

理由：**在斜率设计里安慰剂不构成对照** —— 它没有规模维度，跟它比得到的是一个截距差，
不是斜率。它现在只承担一件事：验「**不是任何检索结果都能提分**」。
所以一次就够，跑三次是白花钱。

## 4.6 污染探针降级为标签

不再作为独立指标、不再有「污染分层后干净样本 < 10 条则实验无效」这条闸门
（阶段 3 已经证明这一关能过：15/30 干净）。改成**给每道 held-out 题打两个标签**：

- `date_vs_cutoff`：事件日期在模型知识截止（2026-05）之前 / 之后
- `publicity`：公开程度（大众媒体级 / 行业报告级 / 仅原始调查文件）

报结果时**按标签分层看斜率是否一致**。斜率在「截止之后 + 仅原始文件」这一层里也成立，
才说明它不是靠模型自己记得这件事。分层不一致要写出来，不许只报合并值。

## 4.7 element-level F1 降为次要指标

阶段 3/4 的条件 F1（`pk/eval3.py` 的 `do_f1`）**继续跑、继续报，但不再是主指标**，
只作为斜率的**辅助佐证**：它和 rubric 主指标的斜率方向一致，结论更硬；方向相反，
就在报告里写明两者偏差方向相反、结论只到「没测稳」为止。

降级的理由已经在阶段 3 结果里写死了：这个 checklist 是同一族模型从同一份源材料写出来的，
它测的是「读题仔细程度」，另一个模型读题面就能收敛到 ~0.82，本身就带天花板。

## 4.8 模型轴（预注册）

**网格 = {haiku-4.5, sonnet-5, opus-5} × {无库, 库30, 库60, 库90}** = 12 个 cell × 30 题。
模型 id：`claude-haiku-4-5` / `claude-sonnet-5` / `claude-opus-5`。
有库臂给 Bash + skill + CLI（agentic，跟阶段 4 一致）；无库臂不给库工具。

**预注册的核心预期：弱模型余量大，斜率应该更陡；opus 余量小，斜率可能接近 0。**
依据：IBM 那篇关于 guideline 的发现 —— guideline 的收益取决于**模型的剩余余量**，
在已经 saturated 的模型上是 **0.0pp**。若这个预期成立，前三阶段在 opus 上反复撞天花板
就不是设计失误，而是被试选错了。

**两个「拿得出手」的判据（任一成立即算主结论成立）：**

- **(i) 斜率在 haiku 上显著为正，且 bootstrap 95% CI 不跨 0。**
- **(ii) haiku + 库90 ≥ opus 裸跑**（同一批题、同一个 judge、同一套 rubric；
  「≥」的口径是 haiku+库90 的均值减 opus 裸跑的均值，其配对 bootstrap 95% CI 下界 ≥ 0）。

**两条都不成立就是 null，按「报结果的规矩」直说**，并且必须分清是「没效果」
还是「没测出来」——后者要指名是什么挡住的（judge 翻转率过高 / CI 太宽 / 天花板 / 样本量）。

**⚠️ 判据 (ii) 的已知弱点（预注册时就写下来）**：(ii) 只比了
「haiku+库90」和「opus 裸跑」，**没有要求 haiku+库90 > haiku 裸跑**。
如果 rubric 在 haiku 上也接近天花板（0–6 的整数尺度很可能如此），
那么 haiku 裸跑本来就 ≈ opus 裸跑，(ii) 会**在库什么都没做的情况下自动成立**。
所以报 (ii) 时**必须同时报 haiku+库90 − haiku 裸跑**：
后者不显著为正时，(ii) 只能算「没有反证」，不能当成「库替代了模型规模」。
网格里已经有 haiku 裸跑这个 cell，不额外花钱。

## 4.9 判定表（预注册）

| 结论 | 判据 |
|---|---|
| **规模有用** | 至少一个模型上斜率 CI 不跨 0 且为正；且 4.6 的分层里方向一致 |
| **库能替代模型规模** | 判据 (ii)：haiku+库90 减 opus 裸跑的配对 CI 下界 ≥ 0 |
| **库变大反而有害** | 斜率 CI 不跨 0 且为负 —— 此时**必须**给出 4.4 的三个数并说明是不是 shadowing |
| **安慰剂有效**（库的作用不来自内容） | 库90 ≈ 盲检索安慰剂（90） |
| **没测出来（不是没效果）** | judge 翻转率 > 10%，或全部 CI 都跨 0 且宽度大于效应量级 |

## 4.10 这一节明确**不做**的事

- 不再改题、不再调难度、不再换主指标（第四条硬规矩）。
- 不再做双判分。
- 不把安慰剂当规模对照。
- 不在看到结果之后改 4.1 的斜率口径（log2 主、线性辅，已经定死）。

## 4.11 成本预估与它带来的风险

12 个 cell × 30 题 = 360 次 agentic 调用，外加 judge（360 × 2 遍翻转率检查）。
阶段 4 的 60 次 opus agentic 调用是 \$119.75，据此 opus 那一行（120 次）约 \$240，
sonnet/haiku 便宜一个量级但不是零，判分另计。**整轮量级在 \$350–450。**

这是一个真实风险，写在预注册里而不是事后解释：**如果预算只够跑一部分，
先砍的是模型轴里的 sonnet 行，不是任何一个规模点** —— 规模点少一个，斜率就只剩两点，
两点连线没有残差、做不出 CI，整个设计就废了。
